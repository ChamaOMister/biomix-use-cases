## Follow-ups from the v1.0.0 review

| Follow-up | Outcome |
| --- | --- |
| The live page reads its reports and filter context without one consistent read transaction | **Closed** (`8193b9c`). `withReadSnapshot` (`src/server/db/pool.ts`) runs the filter options, report, collections and rankings in one `REPEATABLE READ READ ONLY` transaction on one connection. `src/server/db/read-snapshot.test.ts` applies a delivery on another connection between two reads. It then checks that every read inside the transaction still sees the earlier data, that writes are refused (`25006`), and that the connection returns to the pool. Mutation check: with a plain `BEGIN`, both tests fail |
| The snapshot's due-month labels wrap at mobile width | **Closed** (`e44ea51`). Months read "Jan 2025", and table key cells use `white-space: nowrap`. At 390 and 360 px, no key cell is taller than one line, and wide tables scroll inside their card |

## Snapshot brought up to the redesign

Before this change, a v1.1 tag would have published a snapshot that looked like the v1.0.0 one, because the redesign never touched `src/snapshot/`. The snapshot now follows the dashboard:

- a filter bar that applies each change at once, including the customer state, showing names and never IDs
- KPI cards and monthly column charts
- sales by seller, state and business unit
- top products and customers, and every customer
- the collections section in the same style
- light and dark themes

Rankings come from a new pure module, `buildSalesRankings` (`src/domain/sales-report/rankings.ts`), which the stored rankings now share their types and order with. The database tests compare the stored rankings with both the pure rankings of the replayed lines and the rankings of the snapshot's data, in all 16 filter cases. The snapshot data moves to format 2, which adds each customer's state and city, so the state cases also join its parity tests.

These dashboard features stay live-page only: clicking a name to filter, the removable filter chips, and sidebar navigation. The file's Content-Security-Policy forbids inline `style` attributes, so chart geometry uses SVG attributes and hover details use SVG `<title>` elements.

## Findings

Found by a code review of the range at high effort, then checked by hand.

| # | Finding | Outcome |
| --- | --- | --- |
| 1 | **Defect.** On the live page, a date field applied on every input event. While a year was typed digit by digit, each valid partial date (`0002-03-01`) caused a navigation, and the form's remount threw the half-typed date away | **Fixed** (`5b566b9`). Dates now apply when the field is left or Enter is pressed; other filters still apply at once. Tested in headless Chromium against `next start`: typing `03012025` changed no URL and kept focus. Moving focus away applied `from=2025-03-01`, and Enter in To applied `to=2025-12-31` |
| 2 | **Defect.** `groupInvoices` threw when an invoice's lines disagreed on the customer state. The XLSX import does not require that they agree. No screen passes XLSX lines to the collections module today | **Fixed.** The invoice gets no state, so a state filter does not select it. Regression test in `src/domain/collections/report.test.ts` |
| 3 | Duplicate customer or product names would show as identical options | **Fixed.** The new `optionLabels` helper shows "name · ID" only when names collide. The page and the snapshot both use it. The seeded data has no duplicates |
| 4 | A rankings failure showed a generic message | **Fixed.** The page shows the module's message |
| 5 | Every chart column was a tab stop with its own label inside `role="img"`, so screen readers ignored the labels and keyboard users met about 45 extra stops | **Fixed.** Columns are no longer focusable. Each chart has one label, and its exact amounts are in the table that follows it |
| 6 | The customer table's share and the filter bar's unit names duplicated shared helpers | **Fixed.** They now use `share()` and `BUSINESS_UNIT_LABELS` |
| 7 | The page's reads now run one after another instead of in parallel | **Accepted.** pg deprecates overlapping queries on one client, and one connection is needed for one snapshot. Measured: about 0.25 s per page against the development database |
| 8 | The docs describe the old state, including `manual-qa.md`'s Apply and Clear buttons | **Docs updated** in this change. `manual-qa.md` covers the XLSX workbench, which still has those buttons, so it needed no change |
